# 調査モードの設計と実測

ローカルLLMで「ディープリサーチ」——検索して複数の資料を読み、統括して回答する——
を成立させるまでの記録。数値はすべて手元の環境（6GB VRAM）での実測値。

## 到達点

| | 変更前 | 変更後 |
|---|---|---|
| 検索 | 2回 | **7回** |
| 読んだページ | 2件 | **16件** |
| 探索ラウンド | 1周で打ち切り | **3周完走** |
| 資料から取れた要点 | 8件 / 398字 | **121件 / 10,608字** |
| 1ページあたりの要点 | 200字 | **663字** |
| 回答 | 706字 / 3段落 | **1,238字 / 12段落** |
| 所要 | 135秒 | 650秒 |

情報量は約26倍。回答は一次情報が中心になり、資料間の矛盾を丸めず、
ベンチマークで劣る数値も書くようになった。

## 構成

```
plan      質問 → 確認事項・検索語
search    検索（DuckDuckGo、制限時はBingへ切替）
select    検索結果から読むページを選ぶ
read      ★ページ1本につき1回。渡すのは「質問 + そのページ本文」だけ
gaps      不足を洗い出して追加検索（最大3ラウンド）
condense  要点が多すぎる場合、グループごとに中間要約
write     ★全要点を統括。JSONスキーマなし・ストリーミング
```

`read` をページごとに分けるのが要。1回の呼び出しに載るのは常に1ページ分なので、
**ページ数を増やしてもコンテキストは増えない**。大きな `num_ctx` を確保せずに済む。

この形は [GPT Researcher](https://github.com/assafelovic/gpt-researcher) と同じ
（planner が調査質問を作り、資料ごとに個別要約し、集約して報告書にする）。
ページ数 20 は同プロジェクトが採っている値。

## 見つけた問題と対処

### 1. ページ本文の3〜4%しか回答に届いていなかった

これが「浅い」の正体だった。実測した情報の流れ:

```
① HTMLから本文抽出        6,513字
② モデルに渡す            6,513字（9,000字超のみ関連箇所を抜粋）
③ read がまとめた要点        204字  ← ここだけが回答に届く
```

上限は 1,600字あったのに 204字しか書かれていなかった。原因は指示が
「役立つ内容を書き出す」と選択的だったこと。「このページを読むのは
あなただけで、書き出さなかった内容は失われる」「件数を惜しまない」に変えた。

**指示の言い換えだけで 200字 → 663字**。枠を広げるより先に、枠を使い切らせる。

### 2. 探索が1ラウンドで止まっていた

`gaps` が「不足なし」と判断すると打ち切る作りで、8ページ読める設計なのに
2ページで終わっていた。`select` の上限を1ラウンド2件から8件へ、
ラウンドを2→3へ、候補を16→30へ。「視点や発信元が異なる資料を混ぜる」も追加。

### 3. 要点が増えると統括役の窓に入らない

20ページ × 600字 = 12,000字。`num_ctx` を上げるとVRAMを食って遅くなるので、
上限を超えたらグループごとに中間要約して畳む（`condense`）。
`notes.html` の長文要約と同じ多段圧縮。
[local-deep-research の Issue #5718](https://github.com/LearningCircuit/local-deep-research/issues/5718)
が `context_limit * 0.7` で同じことをしている。

### 4. 大きいモデルで全ページを読むと時間がかかりすぎる

`read` と `condense` だけ小さいモデルで動かせるようにした（`createClient` の `readModel`）。
資料が手元にある読解なので小さいモデルで足りる。

| | 20ページの読み取り |
|---|---|
| 9b | 約16分 |
| 4b | **約3分** |

GPT Researcher が gpt-4o-mini と gpt-4o を使い分けているのと同じ構造。
設定画面から選べるようにし、既定は一番小さいモデル。

## 捨てた設計

最初は「引用を原文から抜き出し、回答の各主張と照合する」検証パイプラインだった。
引用の実在確認は機能していた（実測6/6が原文に一致、矛盾する主張も実際に除外された）が、
**検証のためにページを引用へ潰し、その引用だけで書かせていた**ため回答が薄くなった。
出力も「検証済みの主張を並べる」形だったので、事実の断片が並ぶだけで文章にならなかった。

検証をやめ、ページ本文をモデルに読ませる方に振った。

## 残っている課題

- **PDFと大きいページを取得できない。** 最も一次の資料（システムカード）を
  3回試して全部落とした。サイズ上限3MB超過とPDF非対応が原因。
  サーバーに `pdftotext` があるので繋げば解決する
- `missing` に「何が分からないか」ではなく取得失敗したURLが入ることがある
- 小さいモデルに読ませた影響か、カタカナや訳語の乱れが残る

## 設計上の判断

- **最終回答にJSONスキーマをかけない。** かけると事実の断片が並ぶだけになる
- **回答本文に引用番号を書かない。** 出典と要点は「調査の詳細」にまとめる
- **モデルに渡すデータに内部IDを含めない。** 含めるとモデルが引用番号として
  本文に書いてしまい、「書くな」と指示しても止まらない
- **指示は増やさず入れ替える。** 機械側やデータ側で担保できるようになった項目は
  指示から下ろす。不具合のたびに1文足すと、いずれ全体が効かなくなる
